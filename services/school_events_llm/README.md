# school_events_llm

Независимый прототип LLM-сервиса «Школьные события» по актуальному ТЗ v1.5 из `docs/tz/`.

Сервис принимает запрос в формате контракта 01, собирает контекст и prompt-блоки, генерирует от 1 до 3 вариантов через выбранную LLM, проверяет результат Python-кодом и формирует ответ по замороженному контракту 02.

Реализованы CLI-прототип и внутренний HTTP-сервис для подключения к основному Backend Severus. По умолчанию HTTP-сервис запускается на `127.0.0.1:8090`.

## Требования

- Python 3.11 или новее.
- Для реального теста Qwen3.5-9B: LM Studio с локальным сервером на `127.0.0.1:1234`.
- Все служебные операции выполняются через `python -m app ...` и `python -m pytest`.
- `.bat`, `.ps1` и `.sh` не требуются.


```dotenv
SERVICE_AUTH_TOKEN=
```

`LLM_SERVICE_FIXTURE_MODE=true` позволяет проверить полный Backend -> LLM-service -> Backend сценарий без реального провайдера модели. URL и API-ключ внешнего OpenAI-compatible шлюза задаются только через окружение или секреты хостинга.

## Первый тест Qwen3.5-9B

1. Загрузить Qwen3.5-9B в LM Studio.
2. Включить OpenAI-совместимый сервер на порту `1234`.
3. Проверить выбранную модель.
4. Запустить генерацию на одном из примеров.

```bash
python -m app health
python -m app generate examples/requests/ex1_knowledge_day.json
```

Если трассировка включена, артефакты запуска сохраняются в `data/runs/<job_id>/`. Там находятся итоговый `final_result.json`, читаемые варианты, фактические prompt, сырые ответы модели, parsed JSON, манифесты и результаты проверок.

В каждом `calls/call_XXXX/manifest.json` записаны токены вызова (`usage`: вход и выход по данным провайдера), итог за генерацию - в `metadata.json` (`tokens`, с разбивкой по этапам) и в выводе `generate`. Общий журнал всех генераций - `data/runs/runs.jsonl`: одна строка на прогон (событие, модель, статус, вызовы, время, токены, замечания, ошибка), в том числе для неудачных.

```text
python -m app serve [--host HOST] [--port PORT]
python -m app health [--model KEY]
python -m app compose REQUEST.json --stage STAGE [--json]
```

Публичные команды `generate` и `compose` всегда используют `context_mode=full` и включенный культурный контекст. Параметры H2/H3 доступны только через `experiment`. Входной контракт 01 не содержит и не должен содержать экспериментальные флаги.

Этапы модели:

- `variation_plan`
- `scenario_plan`
- `scenario_blocks`
- `scenario_block`
- `materials`
- `quality_review`

`quality_review` вызывается только если `llm_quality_review=true` в `config/generation.json`. Основные структурные проверки в любом случае выполняются Python-кодом.

`batch` прогоняет набор запросов подряд тем же путём, что `generate`, и печатает сводную таблицу: статус, число вызовов, время, токены, критичные замечания и предупреждения. Сводка сохраняется в `data/runs/batch_<время>.md` и `.json`. Набор для проверки разных возрастов, длительностей и режимов участия родителей - `examples/requests/matrix/` (дополняет E2E-набор QA в `qa/tests/fixtures/inputs/`):

```bash
python -m app batch examples/requests/matrix
python -m app batch examples/requests/content_check
python -m app batch examples/requests/variants_1115 --parallel 10
```

`--parallel N` - до N генераций одновременно, как в сервисе (общий предел обращений к модели - `config/service.json`); таблица и трассы те же, в итоге - общее время прогона. По умолчанию запросы идут по очереди. Наборы `qa_check_1114`, `qa_check_1114b` (баг-листы QA) и `variants_1115` (10 запросов на 25 вариантов: разные события, классы, ресурсы и роли родителей) - для повторных проверок на живой модели.

`examples/requests/content_check/` - контрольные запросы по содержанию: Рождество Христово (7 класс, 30 минут), День народного единства (10 класс, 45 минут), День знаний (2 класс, 45 минут, с родителями-помощниками) и региональный День образования Свердловской области (6 класс, 45 минут).

### Устойчивость к ошибкам модели

- **Ошибки провайдера.** Временные ошибки (5xx, таймаут, нет сети) повторяются с паузой: `provider_retry_attempts` и `provider_retry_backoff_seconds` в `config/generation.json`. Для недоступности шлюза (`MODEL_UNAVAILABLE`) - `unavailable_retry_attempts` (4) и `unavailable_backoff_seconds` (3, 10, 20, 30 с), для лимита шлюза (429) - `rate_limit_retry_attempts` (7) и `rate_limit_backoff_seconds` (5, 10, 20, 40, 60, 60, 60 с), но не меньше `Retry-After` шлюза. К паузам добавляется случайный разброс `retry_jitter` (±30%). Таймаут повторяется 2 раза: каждая попытка ждёт до `timeout_seconds`. Ошибки авторизации и настройки не повторяются. Каждый повтор и текст ошибки шлюза пишутся в трассу (`llm_call_retry`).
- **Ответ не по схеме.** Этап повторяется с текстом ошибки (`max_repair_attempts_per_stage`).
- **Исправления до проверки схемы** (`stage_output_fixed` в трассе). Повторный вызов модели с той же ошибкой обычно возвращает тот же ответ, поэтому типовые ошибки формы чинит программа:
  - `material_id` и `role_id` - к виду `^[a-z][a-z0-9_]*$` одинаково во всех ссылках, ID блоков - к `block_NN`;
  - зависимости материалов - только из `catalog/dependencies.json`: синонимы, опечатка в одной букве (`colored_pensils`), цвет перед расходником (`red_paper`) и «X_or_Y» (`sticky_notes_or_tape`) заменяются на ID словаря, ID другого материала варианта убирается (`dependency_is_material`), остальное переносится в `teacher_notes` по-русски («Также понадобится: пайетки, большие картонные коробки»); расходники не становятся материалами и убираются из ссылок блоков;
  - значения перечислений и адресаты материалов - к допустимым (`pupils_all`, `whole_class` - `pupils_group`); механика ценности не из списка - первая разрешённая каталогом для этой ценности (`enum_fallback`), не разрешённая для ценности (`VAL-004`) - ближайшая разрешённая (`mechanic_not_allowed`);
  - тип материала по `material_id` для листа жюри, бюллетеня и памяток; лист голосования без вопросов с ответами - раздаточный материал, чтобы `QUIZ-KEY` не срабатывал зря;
  - число в роли родителей не меньше 1; `family_task` снимается с памятки родителям, бюллетеня и других материалов для взрослых;
  - факт без текста, но с проверенным `fragment_id` получает цитату фрагмента, без проверенного фрагмента выбрасывается.
- **Задание семье** (`VAL-005`) чинится программой, без повторного вызова модели: тип `handout`, пометка «(по желанию, до мероприятия)» в названии и, если альтернатива не найдена, стандартная фраза для ребёнка, которому дома помочь некому (`family_task_fixed` в трассе). Если ценности «Семья» в запросе нет, `family_task` снимается.
- **Голосование без зрителей.** Если выбрано голосование, а модель сделала всех родителей помощниками, голосующими считаются родители из блока голосования. Инструкция к награждению разрешена и по итогам работы жюри.
- **Разбор JSON ответа**: допускаются переносы строк внутри строк и комментарии `// …`; неэкранированная кавычка внутри текста экранируется, а экранированная кавычка, которой модель закрыла строку перед следующим ключом, возвращается на место. `content` материала списком или словарём превращается в текст, пустой `used_in_blocks` заполняется по плану, пустой чек-лист реквизита собирается из названия и заметок, без `groups_count` число групп считает программа; неполный факт (`{"claim": …}`) дополняется, источник не придумывается.
- **Ссылки на материалы.** Блоки ссылаются только на материалы плана; `used_in_blocks` и голосование - только на существующие блоки и материалы (`material_refs_fixed` в трассе).
- **Ошибки задачи в HTTP API** - в формате контракта 02: `field=null` для замечаний проверки, `retryable=true` для отказов по качеству и временных ошибок модели, не больше 5 причин на вариант. Если генерация упала до вариантов - `OUTPUT_SCHEMA_INVALID` или код ошибки модели, без технических подробностей в тексте.

## Режимы full и universal

Состав prompt-блоков задается в `config/experiment_modes.json`.

`full` использует точный класс, предпочтения педагога, профиль школы, реальные ресурсы, региональный и проверенный культурный контекст.

`universal` предназначен только для эксперимента. В этом режиме не подключаются `GRADE`, `TEACHER`, `SCHOOL`, `REGION`, а реальные ресурсы заменяются нейтральным ресурсным профилем. Предпочтения педагога сбрасываются к дефолтам, кроме полей из `keep_teacher_fields` (по умолчанию `script_detail`, чтобы универсальная версия не была короче по полноте). В prompt добавляется блок `MODE`.

Раздел «Справочные данные» подключается во всех режимах. В `universal` фрагменты в него не передаются, поэтому он прямо запрещает фактические утверждения. При `--cultural-context off` отключаются региональные и культурные темы, а фрагменты о самом событии остаются.

Изменение состава экспериментального режима не требует изменения Python-кода генератора.

## Модели и reasoning_mode

Модель выбирается через `ACTIVE_MODEL` в `.env` либо `default_model` в `config/models.json`. Генератор не должен изменяться при смене модели. Для одного прогона без правки `.env` - флаг `--model` у `generate` и `batch`. Рабочая модель проекта - `urfu_gigachat_2_max`.

**Небрежный JSON (`"output_fixes": "lenient"` в профиле, сейчас только `urfu_gigachat_3_pro`).** Для моделей, которые пишут полный ответ, но ломают форму JSON, `jsonx.quote_keys` и `app/generation/lenient.py` чинят форму по схеме этапа и плану: ключи и значения без кавычек, значение без ключа, забытую `}`, опечатки в ключах (`proputed_minutes`, `used_inblocks`), раздел не на своём месте, словарь вместо списка, поля, которые программа знает из плана (`role_ids` блока, `used_in_blocks` материала). Починенный текст берётся, только если обычный разбор не прошёл, а починенный разбирается целиком. Правки пишутся в трассу (`output_shape_fixed`). У профилей без флага (2-Max и остальные) ничего из этого не вызывается.

Для локального Qwen используется OpenAI-совместимый API LM Studio. `model_id: auto_loaded` разрешает автоматически выбрать единственную загруженную модель. Если LM Studio сообщает несколько загруженных моделей, нужно явно задать `model_id`.

`reasoning_mode` и `disable_thinking_method` управляют обработкой рассуждений модели. Независимо от способа отключения reasoning, служебные блоки `<think>` и `<analysis>` не должны попадать в parsed JSON.

**Уровень рассуждений GigaChat** (`reasoning_effort`: `low`, `medium`, `high`). GigaChat API принимает параметр `reasoning_effort` в OpenAI-совместимом формате, шлюз LiteLLM УрФУ передаёт его дальше (проверено 14.11.2026: рассуждения приходят отдельным полем `reasoning_content`, в `content` - только ответ). По умолчанию рассуждения выключены. Включаются:
- для этапа - `tasks.<этап>.reasoning_effort` в `config/generation.json` (например, `"scenario_plan": {..., "reasoning_effort": "medium"}`);
- для модели целиком - `reasoning_effort` в профиле `config/models.json`;
- без правки конфига - `LLM_REASONING` в `.env` (действует для `serve`, `generate`, `batch`; после правки `.env` сервис перезапустить) или разово `python -m app batch <запросы> --reasoning scenario_plan=medium,scenario_block=low`; формат `этап=уровень` через запятую, `*=low` - все этапы. `LLM_REASONING` важнее значения в `config/generation.json`.

Рассуждения расходуют тот же лимит ответа, что и JSON, поэтому для этапа с рассуждениями лимит увеличивается на `reasoning_extra_output_tokens` (2000). Текст рассуждений сохраняется в трассе вызова (`calls/<call>/response.reasoning.txt`), уровень и объём - в `manifest.json` (`reasoning_effort`, `reasoning_chars`); в разбор JSON рассуждения не попадают. Если модель или шлюз не принимают параметр (ответ 400), вызов повторяется без него, генерация не падает. Для моделей с `reasoning_mode: disabled` (Qwen) параметр не передаётся.

## Параллельная работа и очередь

Сервисом пользуется вся школа, поэтому генерации разных педагогов идут одновременно. Настройки - в `config/service.json`:

| Параметр | По умолчанию | Что значит |
|---|---|---|
| `max_parallel_generations` | 30 | сколько генераций идут сразу, без очереди |
| `max_waiting_generations` | 100 | сколько генераций сверх этого ждут со статусом `queued`; если занято и это, `POST /api/v1/generations` отвечает 503 `SERVICE_BUSY` с `retryable: true` |
| `max_parallel_llm_requests` | 10 | общий предел одновременных обращений к модели в процессе; остальные обращения ждут своей очереди внутри сервиса |
| `max_parallel_variants` | 3 | сколько вариантов одной генерации создаются одновременно после общего первого этапа; 1 - по очереди |
| `local_model_max_parallel` | 1 | одновременных обращений к локальной модели (LM Studio на одной видеокарте) |
| `llm_slot_wait_seconds` | 600 | сколько обращение к модели ждёт свободного места; дольше - ошибка `SERVICE_BUSY` (retryable) |
| `results_keep_hours` | 24 | сколько часов статусы и готовые проекты хранятся в памяти сервиса |
| `llm_cache_bypass` | true | не брать ответы из кэша шлюза LiteLLM (см. ниже) |

Варианты одной генерации независимы: каждый строится по своей концепции из общего первого этапа (`variation_plan`) и знает только концепции соседей, а не их результат. Поэтому они создаются одновременно, до `max_parallel_variants`, и генерация идёт примерно как самый долгий вариант; внутри варианта этапы идут по очереди. Если ключ не подходит или модель не настроена (ошибка, которую повтор не исправит), остальные варианты не начинаются и останавливаются на следующем обращении к модели (событие `variant_stopped` в трассе). Временный сбой сети или шлюза после своих повторов валит только свой вариант: соседние доделываются, и фронтенд показывает готовые («Готова часть сценариев»). Номера вызовов, события и токены в трассе считаются под блокировкой. Повтор записанных ответов в тестах (ответы по порядку вызовов) и эталон с битыми ответами идут по очереди.

Одновременных обращений к модели во всём процессе не больше `max_parallel_llm_requests`: сервис принимает 30 генераций сразу, а к шлюзу одновременно идут 10 обращений, остальные ждут места внутри сервиса и не получают отказ. 10 - столько выдерживает лимит шлюза LiteLLM УрФУ для нашего ключа; если лимит поднимут, число можно увеличить. Генерации выполняются в собственном пуле потоков сервиса, и запросы статуса отвечают сразу, даже когда все места заняты.

Задачи изолированы: у каждой свой `job_id` и `project_id`, свой генератор, клиент модели и папка трассы `data/runs/<job_id>/`. Общие у задач только каталог (только чтение) и пределы. Общий журнал `runs.jsonl` пишется под блокировкой, строки разных задач не перемешиваются. Сервис отдаёт статус и проект только по их ID; какой педагог какую задачу видит, решает общий Backend.

**Кэш шлюза.** Шлюз LiteLLM УрФУ отдаёт сохранённый ответ на запрос, совпадающий до символа: одинаковый запрос давал бы тот же сценарий, а повтор исправления - тот же неверный ответ. При `llm_cache_bypass: true` для профилей с `"gateway_cache": true` в `config/models.json` (все `urfu_*`) сервис просит шлюз не читать и не сохранять кэш (`"cache": {"no-cache": true, "no-store": true}`) и добавляет в конец запроса служебную отметку `job_id/call_id`, которая делает каждый вызов уникальным; если шлюз отвечает на параметр кэша ошибкой 400, вызов повторяется без него. В трассе (`prompt.md`) запрос сохраняется без отметки.

Текущая нагрузка: `GET /api/v1/load` (генераций идёт и ждёт, обращений к модели сейчас и пик).

Проверка на запущенном сервисе (`python -m app serve`) - одновременно отправить N генераций и посмотреть, как они прошли:

```bash
python -m app load-test examples/requests/content_check --count 5
python -m app load-test examples/requests/matrix examples/requests/content_check --count 30
```

Сервис хранит задачи в памяти одного процесса: запускать его нужно одним процессом (`python -m app serve`), без нескольких воркеров uvicorn.

Обращения к локальной LLM внутри процесса ограничены `local_model_max_parallel` (по умолчанию по одному).

Если LM Studio одновременно используют другие процессы, можно включить общий lock-файл:

```dotenv
LOCAL_LLM_MUTEX_ENABLED=true
LOCAL_LLM_MUTEX_PATH=data/locks/lm_studio.lock
```

По умолчанию `LOCAL_LLM_MUTEX_ENABLED=false`. Все процессы, которые должны координировать доступ к одной локальной модели, обязаны использовать один и тот же путь lock-файла.

## Каталог событий

Карточки событий и источники сервис читает из общего каталога проекта `severus/catalog/` (путь задаётся `CATALOG_DIR`, по умолчанию `../../catalog`). Своей копии каталога в сервисе нет: в `services/school_events_llm/catalog/` лежат только справочники ценностей и зависимостей материалов.

Из карточки генератор берёт `title`, `category`, `supported_age_groups`, `supported_formats`, `educational_goals`, `values`, `date_rule`, `age_appropriateness_notes`, `facts_to_verify`, `regional_topics`. Смысл события для сценария (акценты, идеи активностей) описан в `prompts/events/<event_id>.md`.

Генератор принимает все события каталога: это тот же список, который бэкенд отдаёт фронтенду (`GET /api/v1/catalog/events`). Отдельных статусов у событий нет: карточка в `catalog/events/` - событие доступно.

При загрузке сервис проверяет каталог и сообщает **все** найденные проблемы сразу: нет обязательного поля, неизвестная ценность, нет совета для поддерживаемой возрастной группы, нет блока `prompts/events/<event_id>.md` и т. п. Проверить каталог без генерации:

```bash
python -m app catalog-check
```

Код выхода 4 означает, что каталог не подходит генератору; список проблем печатается в stderr.

### Текст для педагога и точность события

- **Технические ID в тексте.**
  - В промптах этапов блоков и материалов материалы и этапы названы по-русски: материалы блока программа берёт из плана (`material_ids` модель оставляет пустым), ID материалов этап материалов видит один раз - в списке для поля `material_id`, после названия, а в образцах ответа - пример с настоящим названием («Подготовьте «Маршрутные листы» заранее»).
  - Если ID всё же попал в текст, `app/generation/humanize.py` после сборки варианта заменяет его во всех текстах для педагога (реплики, действия учеников, материалы, памятка, план участия родителей) на название материала, этапа, роли или расходника; поля-ссылки (`material_ids`, `used_in_blocks` и т. п.) не меняются. Названия служебных полей, употреблённые как слово (`fact_claims`, `source_id`, `teacher_notes`), заменяются русскими словами, после предлога - в нужном падеже («в заметках для педагога»). Кусок JSON со ссылками прямо в тексте вырезается, факт с датой перед ним записывается с этим фрагментом.
  - ID с ошибкой ищется по ступеням (`IdMatcher`): точно; те же слова в другом числе и порядке; одно лишнее или пропущенное слово, если оно не меняет смысл (ответы, жюри, родители, памятка); опечатка в одну букву в слове от 5 букв; расходник из словаря. Нестрого ищутся только материалы и расходники, роли и этапы - только точно; подставляется только единственный кандидат, цифры должны совпадать, адреса и имена файлов не трогаются.
  - Замены пишутся в трассу (`tech_ids_replaced`, нестрогие - с полем `matched`). Оставшиеся латинские обозначения и расходники, которые не удалось назвать по-русски в заметке «Также понадобится: …», дают предупреждение `TECH-ID-IN-TEXT` (для заметки - своим сообщением: «остались слова не по-русски»).
  - Фразы о самом сценарии, перенесённые из требований в реплику («Объём текста сценария… около 780 символов»), и английские подписи полей перед текстом пункта и ремарки вида «(Переходит к подготовке следующего блока.)» убираются или переводятся (`meta_text_removed`). Читаемая версия (`scenario.md`) тоже показывает названия этапов и материалов, а не ID.
- **Близкие праздники.** `config/event_boundaries.json`: для каждого события - с чем его путают и чем отличается (строка «Не путать» в промпте события) и признаки чужого праздника в тексте (предупреждение `EVENT-MIXUP`, например Дед Мороз в сценарии о Рождестве). Там же русские названия региональных тем каталога.
- **Факты.** В промпте события - название из каталога, дата, совет для возраста, что нельзя утверждать без источника, региональные темы. Без проверенных фрагментов модель говорит о традициях обобщённо, без годов, веков, имён и происхождения обычаев. Фрагменты с регионом `RU` годятся для любого региона России. Предупреждения:
  - `FACT-UNREGISTERED` - год, дата или век в тексте без записи в `fact_claims` (дата самого события из карточки каталога и год или дата из названия источника события, например дата указа, не считаются);
  - `CULTURE-UNSOURCED` - традиции конкретной страны или народа («в Италии принято…»), которых нет в проверенных фрагментах события; каждое утверждение сверяется с фрагментами отдельно, задания для поиска («Изучите, как…») и открытые вопросы утверждениями не считаются;
  - `DOC-UNSOURCED` - указ, закон, постановление или приказ с номером, датой или тем, кто издал, которых нет в проверенных фрагментах и названиях источников; номер считается номером документа, только если стоит после слова «указ», «закон» и т. п.; указ подтверждает и фрагмент, где сказано «постановил», «повелел»;
  - `GOAL-UNCOVERED` - воспитательная задача из карточки с годом или веком («Знакомство с событиями 1612 года»), если этот год не встречается ни в одном этапе и материале.
- **Ссылки на источники в тексте** («(fact_claims: src_…/frag_…)», «Согласно frag_…, …») `app/generation/source_refs.py` убирает из реплик, материалов и памятки; скобки, где есть смысл кроме ссылки, остаются без ID. Если ссылка ведёт на проверенный фрагмент события и фраза не добавляет к нему своих дат и документов, факт записывается в `fact_claims` (`source_refs_moved` в трассе). Факты, вложенные в пункты содержания материала, тоже переносятся в `fact_claims`, а служебные ключи в текст не попадают.
- **Время внутри этапа** (`app/validation/inner_timing.py`, предупреждение `INNER-TIMING`): станции по кругу (число станций × минуты на станцию; групп больше, чем названных станций, - одна группа всё время ждёт, смен столько же, сколько групп), выступления по очереди (число групп или пар × минуты на каждую больше длительности блока), работа и затем выступления всех групп без регламента (меньше минуты на группу) и сумма отрезков «у вас N минут» больше длительности блока и следующего блока. Параллельная работа групп, выступления по желанию, короткие ответы («каждая группа расскажет по одному моменту»), время на подготовку («пять минут, чтобы подготовиться к выступлению»), время всего занятия («На занятие нам отведено 45 минут») и выступления в следующем этапе противоречием не считаются. Проверка только предупреждает и не запускает исправление: неоднозначное остаётся эксперту.
- **Минуты на выступления в промпте блока** (`block_timing_hints` в `config/generation.json`, по умолчанию включено): деление класса программа считает до этапа блоков, поэтому в строку блока выступлений (по названию; по цели - если название не про подготовку или репетицию) и блока работы групп или пар, после которого дальше нет блока выступлений, добавляются готовые числа: «выступления всех 4 групп: не больше 2 мин на каждую; работа до них тоже входит в 10 мин» Если на каждую меньше 2 минут, строка даёт два варианта, модель выбирает по смыслу блока: коротко или меньше команд - «выступления всех 12 пар: около 45 сек на каждую - хватит на одну-две фразы; для рассказа объедините пары в 4 команды по 2 мин» (объединяются, если команд выходит хотя бы вдвое меньше и групп или пар не меньше 6). `INNER-TIMING` в таком случае считает названное число: «выступят 4 пары», «объедините пары в 4 команды». Организационные блоки (формирование команд, приветствие, итоги), блоки короче 4 минут и работа групп перед блоком выступлений строку не получают. `false` выключает её без правки кода.
- **Станции по кругу в промпте блока** (тот же `block_timing_hints`): блок, где группы проходят станции по кругу («работа на станциях», «квест по станциям»), получает строку «станции по кругу: 4 группы - 4 станции, не больше 4,5 мин на станцию с переходом»; если на станцию выходит меньше 2 минут - предложение взять меньше станций и столько же групп. Один блок-станция («Станция Ремёсел»), объяснение правил и знакомство со станциями строку не получают.
- **Еда и реквизит** (`app/validation/content_rules.py`): `FOOD-TASK` - задание с настоящей едой (готовка в действиях учеников, «приготовить … из ингредиентов», нарезанные овощи, дегустация); рассказ о традициях и карточки кухни без готовки не считаются. Системный промпт (`core/safety.md` 1.1.0) просит без настоящей еды: кулинарная станция - муляжи, рецепт или меню на карточке. `PROPS-MISSING` - педагог раздаёт сувениры, открытки, призы, грамоты, дипломы, значки, а в материалах и памятке их нет; сувениры, которые дети делают сами, не считаются. Оба - предупреждения.
- **План под запрос** (`app/generation/plan_fixes.py`, `plan_fixed` в трассе): роль родителей, на которую ссылается блок, но которой нет в `roles` (`parent_helpers`), добавляется, если родители включены и такой режим разрешён запросом (`parent_role_declared`); если в каком-то этапе одновременно занято больше родителей, чем пришло, уменьшается самая большая роль этого этапа; роли в разных этапах - те же люди в разное время, их число не меняется. При помощниках, жюри и «призе зрительских симпатий» в план добавляются памятка помощникам, лист жюри и инструкция к награждению, если их нет; если этап материалов такой материал не написал, программа добавляет простую версию (`required_material_fallback`).
- **Даты и факты**: год или дата из проверенного фрагмента, не записанные моделью в `fact_claims`, записываются программой (`fragment_facts_registered`); дата подписи в шаблоне письма отдельной строкой заменяется пустым местом ««___» __________ 20__ г.», год в подписи класса, школы или выпуска в шаблоне («Класс 9-а, 2023 год») - на «20__» (`template_dates_blanked`).
- **Объём реплик** (`config/generation.json`, `script_length`): базовая часть плюс часть на минуту блока по детализации; для 1-4 классов норма умножается на `age_factor` (0,7), а промпт возраста просит короткие простые предложения. `SCRIPT-SHORT` - если реплики короче 90% этой нормы (`short_warning_ratio`); в сообщении - сколько символов из нормы и процент.

## Источники и факты

Источники и фрагменты-цитаты хранятся в общем каталоге: `catalog/sources/<event_id>.json`, поля `sources` и `fragments`.

Проверка структуры и покрытия:

```bash
python -m app sources-check
```

`sources-check` проверяет уникальность идентификаторов, статусы, пустые цитаты, разных составителя и проверяющего, ссылки на события и темы, а также то, что у каждого фрагмента указан `source_id` из списка источников корпуса.

В генерацию попадают только фрагменты со статусом `verified`. Фактологические утверждения фиксируются в `fact_claims`. Если утверждение не подтверждено проверенным фрагментом, оно должно быть удалено, заменено либо явно отмечено `needs_teacher_check=true` в разрешенных ТЗ случаях.

Проверенные фрагменты (`verified`) сейчас есть у трёх событий: Новый год, День образования Свердловской области и День народов Среднего Урала. Для остальных событий в генерацию цитаты не попадают, и модель работает без фактических утверждений. Культурное и историческое покрытие до продуктового использования должно быть проверено куратором.

## Конфигурация и воспроизводимость

`config/generation.json` содержит параметры этапов, включая `max_repair_attempts_per_stage` и `temperature_hint`. Если у этапа задан `max_output_tokens_per_variant`, лимит ответа равен этому значению, умноженному на число вариантов, но не больше `max_output_tokens`. Так настроен `variation_plan`: 1300 токенов на концепцию, потолок 3900, чтобы ответ с тремя концепциями не обрезался.

`fallback` в `config/models.json` и `language`, `max_variants`, `allow_partial_result` в `config/generation.json` - поля из примера конфигурации в ТЗ; сервис их не читает: язык берётся из запроса, число вариантов - из `variants_count`, готовые варианты отдаются и при частичном результате (`partial`). Пределы одновременных обращений к модели задаются в `config/service.json`.

`config/experiment_modes.json` определяет состав контекста экспериментов.

`config/school_profile.json` содержит серверный профиль школы.

Манифест каждого LLM-вызова сохраняет фактически использованные prompt-блоки, версии, SHA-256, использованные переменные, режим контекста и контрольные суммы конфигураций и источников. Это позволяет разбирать конкретную генерацию после изменения prompt или конфигурации.

## Что проверяется автоматически

Тесты покрывают входной контракт и серверные дефолты, сборку prompt, режимы full/universal, точный тайминг, группировку школьников, родителей, ресурсы, ценности, семейное задание, фактологические ссылки, рендер контракта 02, repair, трассировку, Model Router, reasoning stripping, общий lock-файл, проверку общего каталога событий и корпуса источников.

Ресурсы: при отсутствии интернета `RESOURCE-INTERNET` срабатывает на задание, которому нужен интернет («найдите в интернете», «воспользуйтесь интернетом», «отсканируйте QR-код», «онлайн-опрос»), а не на упоминание («кто-то видел примеры в интернете», «как общаться онлайн» как тема урока).

Замечание в `quality_report.issues` - в формате ТЗ 16.2 (`app/validation/issue_format.py`): `issue_id` (`Q-001` по порядку в варианте), `code`, `severity`, `category` (`resources`, `timing`, `facts`, `roles`, `parents`, `voting`, `materials`, `values`, `diversity`, `text`, `structure`, по коду замечания), `location`, `message`, `repairable` и `suggested_action` (подсказка по коду или `null`).

Актуальное количество успешно выполненных тестов следует смотреть в выводе `python -m pytest`. README намеренно не фиксирует число тестов, чтобы оно не устаревало после добавления новых проверок.

Внутренний HTTP API на `127.0.0.1:8090` уже реализован и используется интеграционным контуром Backend -> LLM-service. Пул генераций, очередь задач и хранилище проектов находятся в памяти процесса (см. «Параллельная работа и очередь»). Постоянное хранилище, распределённая очередь, CSV-аналитика и полный Replay остаются последующими этапами.
