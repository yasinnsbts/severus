# school_events_llm

Независимый прототип LLM-сервиса «Школьные события» по актуальному ТЗ v1.5 из `docs/tz/`.

Сервис принимает запрос в формате контракта 01, собирает контекст и prompt-блоки, генерирует от 1 до 3 вариантов через выбранную LLM, проверяет результат Python-кодом и формирует ответ по замороженному контракту 02.

Реализованы CLI-прототип и внутренний HTTP-сервис для подключения к основному Backend Severus. По умолчанию HTTP-сервис запускается на `127.0.0.1:8090`.

## Требования

- Python 3.11 или новее.
- Для реального теста Qwen3.5-9B: LM Studio с локальным сервером на `127.0.0.1:1234`.
- Все служебные операции выполняются через `python -m app ...` и `python -m pytest`.
- `.bat`, `.ps1` и `.sh` не требуются.

```

```

`LLM_SERVICE_FIXTURE_MODE=true` позволяет проверить полный Backend -> LLM-service -> Backend сценарий без реального провайдера модели. URL и API-ключ внешнего OpenAI-compatible шлюза задаются только через окружение или секреты хостинга.

## Первый тест Qwen3.5-9B

1. Загрузить Qwen3.5-9B в LM Studio.
2. Включить OpenAI-совместимый сервер на порту `1234`.
3. Проверить выбранную модель.
4. Запустить генерацию на одном из примеров.

```bash
python -m app health
python -m app generate examples/requests/ex1_knowledge_day.json
```

Если трассировка включена, артефакты запуска сохраняются в `data/runs/<job_id>/`. Там находятся итоговый `final_result.json`, читаемые варианты, фактические prompt, сырые ответы модели, parsed JSON, манифесты и результаты проверок.

В каждом `calls/call_XXXX/manifest.json` записаны токены вызова (`usage`: вход и выход по данным провайдера), итог за генерацию - в `metadata.json` (`tokens`, с разбивкой по этапам) и в выводе `generate`. Общий журнал всех генераций - `data/runs/runs.jsonl`: одна строка на прогон (событие, модель, статус, вызовы, время, токены, замечания, ошибка), в том числе для неудачных.

## CLI

```text
python -m app serve [--host HOST] [--port PORT]
python -m app health [--model KEY]
python -m app compose REQUEST.json --stage STAGE [--json]
python -m app generate REQUEST.json [--model KEY] [--out FILE]
python -m app batch REQUEST.json|ПАПКА ... [--model KEY]
python -m app experiment REQUEST.json --context-mode full|universal --cultural-context on|off [--experiment-tag TAG] [--experiment-pair-id ID]
python -m app validate PACKAGE.json --request REQUEST.json
python -m app render PACKAGE.json --request REQUEST.json [--markdown]
python -m app export-schemas
python -m app sources-check
python -m app catalog-check
```

Публичные команды `generate` и `compose` всегда используют `context_mode=full` и включенный культурный контекст. Параметры H2/H3 доступны только через `experiment`. Входной контракт 01 не содержит и не должен содержать экспериментальные флаги.

Этапы модели:

- `variation_plan`
- `scenario_plan`
- `scenario_blocks`
- `scenario_block`
- `materials`
- `quality_review`

`quality_review` вызывается только если `llm_quality_review=true` в `config/generation.json`. Основные структурные проверки в любом случае выполняются Python-кодом.

`batch` прогоняет набор запросов подряд тем же путём, что `generate`, и печатает сводную таблицу: статус, число вызовов, время, токены, критичные замечания и предупреждения. Сводка сохраняется в `data/runs/batch_<время>.md` и `.json`. Набор для проверки разных возрастов, длительностей и режимов участия родителей - `examples/requests/matrix/` (дополняет E2E-набор QA в `qa/tests/fixtures/inputs/`):

```bash
python -m app batch examples/requests/matrix
python -m app batch examples/requests/content_check
python -m app batch examples/requests/qa_check_1114c --parallel 10
```

`--parallel N` - до N генераций одновременно, как в сервисе (общий предел обращений к модели - `config/service.json`); вывод каждой генерации перехватывается отдельно, таблица и трассы те же, в итоге - общее время прогона. По умолчанию запросы идут по очереди. Наборы `qa_check_1114`, `qa_check_1114b` (баг-листы QA) и `qa_check_1114c` (разные события, классы, ресурсы и роли родителей) - для повторных проверок на живой модели.

`examples/requests/content_check/` - контрольные запросы по содержанию: Рождество Христово (7 класс, 30 минут), День народного единства (10 класс, 45 минут), День знаний (2 класс, 45 минут, с родителями-помощниками) и региональный День образования Свердловской области (6 класс, 45 минут).

### Устойчивость к ошибкам модели

- **Ошибки провайдера.** Временные ошибки (5xx, таймаут, нет сети) повторяются с паузой: `provider_retry_attempts` и `provider_retry_backoff_seconds` в `config/generation.json`. Для лимита шлюза (429) - свои, больше: `rate_limit_retry_attempts` (5) и `rate_limit_backoff_seconds` (5, 10, 20, 40, 60 с); если шлюз прислал `Retry-After`, пауза не меньше неё. К паузам добавляется случайный разброс `retry_jitter` (±30%), чтобы генерации, получившие отказ одновременно, не возвращались в шлюз одной пачкой. В сообщение об ошибке и в трассу попадает текст шлюза - какой лимит сработал. Ошибки авторизации и настройки не повторяются. Каждый повтор пишется в трассу (`llm_call_retry`).
- **Ответ не по схеме.** Этап повторяется с текстом ошибки (`max_repair_attempts_per_stage`).
- **Исправления до проверки схемы** (`stage_output_fixed` в трассе): `material_id` и `role_id` приводятся к виду `^[a-z][a-z0-9_]*$` одинаково во всех ссылках, ID блоков - к `block_NN`; зависимости материалов - только из `catalog/dependencies.json` (синонимы заменяются, остальное переносится в `teacher_notes`); значения перечислений и адресаты материалов - к допустимым; тип материала по `material_id` для листа жюри, бюллетеня и памяток (`jury_scorecard` с типом `quiz` - `jury_scorecard`); лист голосования с типом «викторина» (без вопросов с ответами) - раздаточный материал, чтобы `QUIZ-KEY` не срабатывал зря; число в роли родителей не меньше 1; факт без текста, но с проверенным `fragment_id` получает цитату фрагмента, без проверенного фрагмента выбрасывается; механика ценности, которую не удалось распознать (`sharing`), - первая разрешённая каталогом для этой ценности (`enum_fallback`), а распознанная, но не разрешённая для ценности (`VAL-004`), - ближайшая разрешённая (`mechanic_not_allowed`): GigaChat на просьбу исправить такое значение возвращал тот же ответ; расходники не становятся материалами и убираются из ссылок блоков; `family_task` снимается с памятки родителям, бюллетеня и других материалов для взрослых.
- **Задание семье** (`VAL-005`) чинится программой, без повторного вызова модели: тип `handout`, пометка «(по желанию, до мероприятия)» в названии и, если альтернатива не найдена, стандартная фраза для ребёнка, которому дома помочь некому (`family_task_fixed` в трассе). Если ценности «Семья» в запросе нет, `family_task` снимается.
- **Голосование без зрителей.** Если выбрано голосование, а модель сделала всех родителей помощниками, голосующими считаются родители из блока голосования. Инструкция к награждению разрешена и по итогам работы жюри.
- **Разбор JSON ответа**: допускаются переносы строк внутри строк, комментарии `// …` убираются, неэкранированная кавычка внутри текста («…дружно!" (Через 10 минут…») экранируется. `content` материала списком или словарём превращается в текст, пустой `used_in_blocks` - в блоки, которые ссылаются на материал по плану, пустой чек-лист реквизита собирается из названия и заметок, без `groups_count` число групп считает программа; факт вида `{"claim": …}` без `claim_id`, `text` и `location` дополняется (источник не придумывается).
- **Ссылки на материалы.** Блоки ссылаются только на материалы плана; `used_in_blocks` и голосование - только на существующие блоки и материалы (`material_refs_fixed` в трассе).
- **Ошибки задачи в HTTP API** - в формате контракта 02: `field=null` для замечаний проверки, `retryable=true` для отказов по качеству и временных ошибок модели, не больше 5 причин на вариант. Если генерация упала до вариантов - `OUTPUT_SCHEMA_INVALID` или код ошибки модели, без технических подробностей в тексте.

## Режимы full и universal

Состав prompt-блоков задается в `config/experiment_modes.json`.

`full` использует точный класс, предпочтения педагога, профиль школы, реальные ресурсы, региональный и проверенный культурный контекст.

`universal` предназначен только для эксперимента. В этом режиме не подключаются `GRADE`, `TEACHER`, `SCHOOL`, `REGION`, а реальные ресурсы заменяются нейтральным ресурсным профилем. Предпочтения педагога сбрасываются к дефолтам, кроме полей из `keep_teacher_fields` (по умолчанию `script_detail`, чтобы универсальная версия не была короче по полноте). В prompt добавляется блок `MODE`.

Раздел «Справочные данные» подключается во всех режимах. В `universal` фрагменты в него не передаются, поэтому он прямо запрещает фактические утверждения. При `--cultural-context off` отключаются региональные и культурные темы, а фрагменты о самом событии остаются.

Изменение состава экспериментального режима не требует изменения Python-кода генератора.

## Модели и reasoning_mode

Модель выбирается через `ACTIVE_MODEL` в `.env` либо `default_model` в `config/models.json`. Генератор не должен изменяться при смене модели.

Для локального Qwen используется OpenAI-совместимый API LM Studio. `model_id: auto_loaded` разрешает автоматически выбрать единственную загруженную модель. Если LM Studio сообщает несколько загруженных моделей, нужно явно задать `model_id`.

`reasoning_mode` и `disable_thinking_method` управляют обработкой рассуждений модели. Независимо от способа отключения reasoning, служебные блоки `<think>` и `<analysis>` не должны попадать в parsed JSON.

**Уровень рассуждений GigaChat** (`reasoning_effort`: `low`, `medium`, `high`). GigaChat API принимает параметр `reasoning_effort` в OpenAI-совместимом формате, шлюз LiteLLM УрФУ передаёт его дальше (проверено 14.11.2026: рассуждения приходят отдельным полем `reasoning_content`, в `content` - только ответ). По умолчанию рассуждения выключены. Включаются:
- для этапа - `tasks.<этап>.reasoning_effort` в `config/generation.json` (например, `"scenario_plan": {..., "reasoning_effort": "medium"}`);
- для модели целиком - `reasoning_effort` в профиле `config/models.json`;
- без правки конфига - `LLM_REASONING` в `.env` (действует для `serve`, `generate`, `batch`; после правки `.env` сервис перезапустить) или разово `python -m app batch <запросы> --reasoning scenario_plan=medium,scenario_block=low`; формат `этап=уровень` через запятую, `*=low` - все этапы. `LLM_REASONING` важнее значения в `config/generation.json`.

Рассуждения расходуют тот же лимит ответа, что и JSON, поэтому для этапа с рассуждениями лимит увеличивается на `reasoning_extra_output_tokens` (2000). Текст рассуждений сохраняется в трассе вызова (`calls/<call>/response.reasoning.txt`), уровень и объём - в `manifest.json` (`reasoning_effort`, `reasoning_chars`); в разбор JSON рассуждения не попадают. Если модель или шлюз не принимают параметр (ответ 400), вызов повторяется без него, генерация не падает. Для моделей с `reasoning_mode: disabled` (Qwen) параметр не передаётся.

## Параллельная работа и очередь

Сервисом пользуется вся школа, поэтому генерации разных педагогов идут одновременно. Настройки - в `config/service.json`:

| Параметр | По умолчанию | Что значит |
|---|---|---|
| `max_parallel_generations` | 30 | сколько генераций идут сразу, без очереди |
| `max_waiting_generations` | 100 | сколько генераций сверх этого ждут со статусом `queued`; если занято и это, `POST /api/v1/generations` отвечает 503 `SERVICE_BUSY` с `retryable: true` |
| `max_parallel_llm_requests` | 10 | общий предел одновременных обращений к модели в процессе; остальные обращения ждут своей очереди внутри сервиса |
| `local_model_max_parallel` | 1 | одновременных обращений к локальной модели (LM Studio на одной видеокарте) |
| `llm_slot_wait_seconds` | 600 | сколько обращение к модели ждёт свободного места; дольше - ошибка `SERVICE_BUSY` (retryable) |
| `results_keep_hours` | 24 | сколько часов статусы и готовые проекты хранятся в памяти сервиса |
| `llm_cache_bypass` | true | не брать ответы из кэша шлюза LiteLLM (см. ниже) |

Каждая генерация обращается к модели последовательно, а одновременных обращений к модели не больше `max_parallel_llm_requests`. Почему 10, а не 30: шлюз LiteLLM УрФУ при 30 одновременных обращениях отвечает 429 «превышен лимит запросов» (нагрузочный прогон 14.11: 21 из 30 генераций не прошли), а при 10 справляется (10 из 10). Поэтому сервис принимает 30 генераций сразу, но к шлюзу одновременно идут 10 обращений, остальные ждут места внутри сервиса и не получают отказ. Если администраторы шлюза поднимут лимит для нашего ключа, число можно увеличить. Генерации выполняются в собственном пуле потоков сервиса, и запросы статуса отвечают сразу, даже когда все места заняты.

Задачи изолированы: у каждой свой `job_id` и `project_id`, свой генератор, клиент модели и папка трассы `data/runs/<job_id>/`. Общие у задач только каталог (только чтение) и пределы. Общий журнал `runs.jsonl` пишется под блокировкой, строки разных задач не перемешиваются. Сервис отдаёт статус и проект только по их ID; какой педагог какую задачу видит, решает общий Backend.

**Кэш шлюза.** Шлюз LiteLLM УрФУ отдаёт сохранённый ответ на запрос, совпадающий до символа: такой вызов занимает доли секунды вместо 20-90 с. Из-за этого одинаковый запрос давал тот же сценарий, а повтор исправления с теми же ошибками - тот же неверный ответ. При `llm_cache_bypass: true` для профилей с `"gateway_cache": true` в `config/models.json` (все `urfu_*`) сервис просит шлюз не читать и не сохранять кэш (`"cache": {"no-cache": true, "no-store": true}`) и добавляет в конец запроса служебную отметку `job_id/call_id`. Отметка делает каждый вызов уникальным, даже если шлюз параметр кэша не учитывает; если шлюз отвечает на параметр ошибкой 400, сервис повторяет вызов без него. В трассе (`prompt.md`) запрос сохраняется без отметки.

Текущая нагрузка: `GET /api/v1/load` (генераций идёт и ждёт, обращений к модели сейчас и пик).

Проверка на запущенном сервисе (`python -m app serve`) - одновременно отправить N генераций и посмотреть, как они прошли:

```bash
python -m app load-test examples/requests/content_check --count 5
python -m app load-test examples/requests/matrix examples/requests/content_check --count 30
```

Сервис хранит задачи в памяти одного процесса: запускать его нужно одним процессом (`python -m app serve`), без нескольких воркеров uvicorn.

Обращения к локальной LLM внутри процесса ограничены `local_model_max_parallel` (по умолчанию по одному).

Если LM Studio одновременно используют другие процессы, можно включить общий lock-файл:

```dotenv
LOCAL_LLM_MUTEX_ENABLED=true
LOCAL_LLM_MUTEX_PATH=data/locks/lm_studio.lock
```

По умолчанию `LOCAL_LLM_MUTEX_ENABLED=false`. Все процессы, которые должны координировать доступ к одной локальной модели, обязаны использовать один и тот же путь lock-файла.

## Каталог событий

Карточки событий и источники сервис читает из общего каталога проекта `severus/catalog/` (путь задаётся `CATALOG_DIR`, по умолчанию `../../catalog`). Своей копии каталога в сервисе нет: в `services/school_events_llm/catalog/` лежат только справочники ценностей и зависимостей материалов.

Из карточки генератор берёт `title`, `category`, `supported_age_groups`, `supported_formats`, `educational_goals`, `values`, `date_rule`, `age_appropriateness_notes`, `facts_to_verify`, `regional_topics`. Смысл события для сценария (акценты, идеи активностей) описан в `prompts/events/<event_id>.md`.

Генератор принимает все события каталога: это тот же список, который бэкенд отдаёт фронтенду (`GET /api/v1/catalog/events`). Отдельных статусов у событий нет: карточка в `catalog/events/` - событие доступно.

При загрузке сервис проверяет каталог и сообщает **все** найденные проблемы сразу: нет обязательного поля, неизвестная ценность, нет совета для поддерживаемой возрастной группы, нет блока `prompts/events/<event_id>.md` и т. п. Проверить каталог без генерации:

```bash
python -m app catalog-check
```

Код выхода 4 означает, что каталог не подходит генератору; список проблем печатается в stderr.

### Текст для педагога и точность события

- **Технические ID в тексте.** На этапе блоков модель знает материалы плана, но не их тексты, и иногда пишет в репликах ID: «(раздаёт heart_cards)», «в блоке block_03». После сборки варианта `app/generation/humanize.py` заменяет известные ID во всех текстах для педагога (реплики, действия учеников, материалы, памятка, план участия родителей) на названия материалов, этапов, ролей и расходников; поля-ссылки (`material_ids`, `used_in_blocks` и т. п.) не меняются. Замены пишутся в трассу (`tech_ids_replaced`). Читаемая версия (`scenario.md`) тоже показывает названия этапов и материалов, а не ID. Оставшиеся латинские обозначения дают предупреждение `TECH-ID-IN-TEXT`. Фразы о самом сценарии, которые модель переносит из требований в реплику («Объём текста сценария… около 780 символов»), и английские подписи полей перед текстом пункта («side_a:» убирается, «station_name:» - «Станция:») меняются только в тексте, поля JSON не трогаются (`meta_text_removed` в трассе). В плане у материалов есть `title`, чтобы модель сразу называла их по-русски.
- **Близкие праздники.** `config/event_boundaries.json`: для каждого события - с чем его путают и чем отличается (строка «Не путать» в промпте события) и признаки чужого праздника в тексте (предупреждение `EVENT-MIXUP`, например Дед Мороз в сценарии о Рождестве). Там же русские названия региональных тем каталога.
- **Факты.** В промпте события - название из каталога, дата, совет для возраста, что нельзя утверждать без источника, региональные темы. Без проверенных фрагментов модель говорит о традициях обобщённо, без годов, веков, имён и происхождения обычаев; годы, даты и века в тексте без записи в `fact_claims` дают `FACT-UNREGISTERED` (дата самого события из карточки каталога не считается). Сведения о традициях конкретной страны или народа («в Италии принято…», «у народов Сибири…»), которых нет в проверенных фрагментах события, дают `CULTURE-UNSOURCED`: каждое утверждение сверяется с фрагментами отдельно (задания для поиска «Изучите, как…» и открытые вопросы «Какой…?» утверждениями не считаются), и источник о дате Рождества не подтверждает традиции Японии. Текст перед поиском приводится к нижнему регистру («В Японии…» и «в Японии…» одинаковы). Фрагменты с регионом `RU` годятся для любого региона России; ссылки на документы (указ, закон, постановление, приказ с номером, датой или тем, кто издал), которых нет в проверенных фрагментах, дают `DOC-UNSOURCED` (номер считается номером документа, только если стоит рядом со словом «указ», «закон» и т. п.; указ подтверждает и фрагмент, где сказано «постановил», «повелел»). Факты, которые модель вложила в пункты содержания материала (`{"text": …, "fact_claims": [{"fragment_id": …}]}`), переносятся в `fact_claims` с текстом пункта, а служебные ключи в текст не попадают. Ссылки на источники, вставленные моделью прямо в текст («(fact_claims: src_…/frag_…)», «(frag_…, frag_…)», «(fragment_id: frag_…)», «Согласно frag_…, …»), `app/generation/source_refs.py` убирает из реплик, материалов и памятки; скобки, где есть смысл кроме ссылки, остаются без ID; если ссылка ведёт на проверенный фрагмент события и фраза не добавляет к нему своих дат и документов, факт записывается в `fact_claims` (трасса `source_refs_moved`); в списках страна берётся из заголовка («Италия:», а ниже «- Украшают вертеп»). Воспитательная задача из карточки с годом или веком («Знакомство с событиями 1612 года»), если этот год не встречается ни в одном этапе и материале, даёт `GOAL-UNCOVERED`: задача в шапке сценария заявлена, но не раскрыта.
- **Время внутри этапа** (`app/validation/inner_timing.py`, предупреждение `INNER-TIMING`): станции по кругу (каждая команда проходит все станции подряд: число станций × минуты на станцию; вводный этап, который только объявляет маршрут для следующих этапов-станций, не считается), выступления по очереди (число групп или пар × минуты на каждую больше длительности блока; формы «по 3 минуты», «3 минуты на группу», «группы по очереди…», «время выступления - 3 минуты», «спикеру даётся 3 минуты», «по минуте на каждую группу»), работа и затем выступления всех групп без регламента (на выступления остаётся меньше минуты на группу) и сумма отрезков «у вас N минут» больше длительности блока и следующего блока. Параллельная работа групп, выступления по желанию и объявление времени следующего этапа не считаются противоречием; выступления не считаются частью этапа, если группы выступают в следующем этапе с уже сделанной работой (по названию или по тексту следующего этапа). Всё неоднозначное остаётся эксперту: проверка только предупреждает и не запускает исправление.
- **План под запрос** (`app/generation/plan_fixes.py`, `plan_fixed` в трассе): если в каком-то этапе одновременно занято больше родителей, чем пришло (12 помощников + 1 зритель при 12 родителях), уменьшается самая большая роль этого этапа (11 + 1); роли в разных этапах - те же люди в разное время, их число не меняется; при помощниках, жюри и «призе зрительских симпатий» в план добавляются памятка помощникам, лист жюри и инструкция к награждению, если их нет. Если этап материалов такой материал не написал, программа добавляет простую версию (`required_material_fallback`). Повторные вызовы модели ради этого не нужны: GigaChat на просьбу исправить часто возвращает тот же ответ.
- **Даты и факты**: год или дата из проверенного фрагмента, не записанные моделью в `fact_claims`, записываются программой (`fragment_facts_registered`); дата подписи в шаблоне письма отдельной строкой заменяется пустым местом ««___» __________ 20__ г.» (`template_dates_blanked`). Неизвестные расходники в заметке педагогу - по-русски («конверты»), без латинских ID.
- **Объём реплик** (`config/generation.json`, `script_length`): базовая часть плюс часть на минуту блока по детализации; для 1-4 классов норма умножается на `age_factor` (0,7), а промпт возраста просит короткие простые предложения. `SCRIPT-SHORT` - если реплики короче 90% этой нормы (`short_warning_ratio`): недобор в несколько процентов модель делает постоянно, это не повод для замечания эксперту; в сообщении - сколько символов из нормы и процент.

## Источники и факты

Источники и фрагменты-цитаты хранятся в общем каталоге: `catalog/sources/<event_id>.json`, поля `sources` и `fragments`.

Проверка структуры и покрытия:

```bash
python -m app sources-check
```

`sources-check` проверяет уникальность идентификаторов, статусы, пустые цитаты, разных составителя и проверяющего, ссылки на события и темы, а также то, что у каждого фрагмента указан `source_id` из списка источников корпуса.

В генерацию попадают только фрагменты со статусом `verified`. Фактологические утверждения фиксируются в `fact_claims`. Если утверждение не подтверждено проверенным фрагментом, оно должно быть удалено, заменено либо явно отмечено `needs_teacher_check=true` в разрешенных ТЗ случаях.

Проверенные фрагменты (`verified`) сейчас есть у трёх событий: Новый год, День образования Свердловской области и День народов Среднего Урала. Для остальных событий в генерацию цитаты не попадают, и модель работает без фактических утверждений. Культурное и историческое покрытие до продуктового использования должно быть проверено куратором.

## Конфигурация и воспроизводимость

`config/generation.json` содержит параметры этапов, включая `max_repair_attempts_per_stage` и `temperature_hint`. Если у этапа задан `max_output_tokens_per_variant`, лимит ответа равен этому значению, умноженному на число вариантов, но не больше `max_output_tokens`. Так настроен `variation_plan`: 1300 токенов на концепцию, потолок 3900, чтобы ответ с тремя концепциями не обрезался.

`config/experiment_modes.json` определяет состав контекста экспериментов.

`config/school_profile.json` содержит серверный профиль школы.

Манифест каждого LLM-вызова сохраняет фактически использованные prompt-блоки, версии, SHA-256, использованные переменные, режим контекста и контрольные суммы конфигураций и источников. Это позволяет разбирать конкретную генерацию после изменения prompt или конфигурации.

## Что проверяется автоматически

Тесты покрывают входной контракт и серверные дефолты, сборку prompt, режимы full/universal, точный тайминг, группировку школьников, родителей, ресурсы, ценности, семейное задание, фактологические ссылки, рендер контракта 02, repair, трассировку, Model Router, reasoning stripping, общий lock-файл, проверку общего каталога событий и корпуса источников.

Ресурсы: при отсутствии интернета `RESOURCE-INTERNET` срабатывает на задание, которому нужен интернет («найдите в интернете», «воспользуйтесь интернетом», «отсканируйте QR-код», «онлайн-опрос»), а не на упоминание («кто-то видел примеры в интернете», «как общаться онлайн» как тема урока).

Актуальное количество успешно выполненных тестов следует смотреть в выводе `python -m pytest`. README намеренно не фиксирует число тестов, чтобы оно не устаревало после добавления новых проверок.
